# Source Body Contract Design

## Goal

Give newly imported GetNote notes a portable, explicit boundary around remote
source text. The boundary lets the plugin preserve source Markdown exactly,
keep local presentation blocks outside the source text, and safely select the
right content when a user later creates a remote note from a marked file.

## Scope

- Add a versioned source-body marker contract to newly rendered notes.
- Store a portable base fingerprint in frontmatter for future conflict work.
- Preserve source Markdown except for normalising line endings to LF.
- Make reverse creation upload the marked source body when a valid boundary is
  present; preserve the current full-body behaviour for unmarked local notes.
- Reject invalid marker contracts instead of guessing a body.
- Make template rendering deterministic for the source-body insertion point.
- Prevent an imported note from overwriting a same-name file that has no
  matching GetNote UID.
- Add fixture-driven Markdown round-trip coverage for both API transport
  shapes.

## Non-goals

- Do not update existing remote notes.
- Do not automatically migrate, scan, or rewrite existing synced notes.
- Do not introduce a sidecar database or Node-only dependency.
- Do not convert arbitrary HTML into Markdown.
- Do not change release versions or existing authentication behaviour.

## File Contract

Newly rendered notes use the following plugin-owned fields and comments:

```markdown
---
uid: "123"
title: "A remote title"
dedao_sync_schema: 1
dedao_source_hash: "sha256:<hex>"
---

Local template text and generated blocks may appear here.

<!-- dedao-brain-sync:source-body:start -->
Remote source body
<!-- dedao-brain-sync:source-body:end -->

Local attachment, transcript, original-link, and relation blocks may appear here.
```

The marker lines are a framing protocol, not part of source text. Rendering
always inserts exactly one LF after the start line and exactly one LF before
the end line. Extraction removes those two framing LFs only, so source text
that begins or ends with one or more LFs round-trips unchanged after LF
normalisation.

The source body must not itself contain either marker line. If it does, the
renderer fails that note without creating or modifying a file.

`dedao_source_hash` is SHA-256 of a canonical JSON object containing the
file-visible title, sorted de-duplicated file-visible tags, and the LF-
normalised source body. The implementation must be platform-neutral: no Node
`crypto` import and identical output on desktop and mobile.

## Rendering and Templates

Rendering is split into three parts: frontmatter, local generated blocks, and
the source-body block. Audio players, transcripts, attachments, original-link
blocks, and parent/child links are generated outside the source-body block.

The `{{content}}` template placeholder means the single source-body insertion
point. A template may omit it, in which case the complete source-body block is
appended after template body content. A template may contain it once. A second
occurrence, or any occurrence in template frontmatter, is invalid and fails
that note before any vault write. `{{title}}` keeps its current behaviour.

Plugin-owned frontmatter fields supplied by a template are removed and
regenerated by the plugin, including the two new contract fields.

## Reverse Creation

When reverse creation reads a file:

- A valid single marker pair means upload exactly the extracted source body.
- No marker pair means preserve existing behaviour and upload the complete
  body after frontmatter.
- A malformed pair, duplicate pair, reversed pair, or invalid framing means
  skip the file with a specific result message. It must not fall back to
  uploading the complete body.

The existing image-to-link conversion applies after body selection. Existing
remote-exists checks and create-only behaviour are unchanged.

## Same-name Write Safety

The UID index remains authoritative. If the desired filename already exists
and it does not have the incoming note UID, the sync engine creates a
conflict-suffixed path and never modifies the existing file. The same rule
applies when a create races with another process. A matching UID remains
skipped under the current incremental-sync contract.

## Markdown Fidelity Tests

Tests use small, non-private fixture bodies that model both OpenAPI and Web
API payload forms. Every fixture verifies:

1. the body becomes the sole source-body region;
2. extraction returns the original after LF normalisation;
3. generated audio, transcript, attachment, and relation blocks are outside
   the boundary;
4. reverse creation selects the boundary body and not generated blocks.

Fixtures cover nested and mixed lists, GFM tables, quotes, task lists, inline
and fenced code, emphasis/highlight/strikethrough, math, Unicode and emoji,
links and images, leading/trailing blank lines, and audio content.

## Acceptance Criteria

- New default and templated imports write one valid source-body pair and the
  two contract frontmatter fields.
- Source-body extraction is LF-stable and preserves leading and trailing blank
  lines.
- Invalid markers fail safely without a vault modification or remote create.
- A marked file selected for reverse creation uploads only marked text.
- An unmarked local file keeps existing reverse-create behaviour.
- An unrelated same-name file is never overwritten by import, including the
  create-race path.
- Focused tests, typecheck, lint, full test suite, and build pass.
